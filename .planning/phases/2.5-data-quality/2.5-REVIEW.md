## Summary

Reviewed the Phase 2.5 data quality pipeline: JSONL conversion, verse marker detection/splitting, text normalization, and validation. The overall architecture is sound — modules are well-structured with clear separation of concerns, thorough test coverage, and good use of dataclasses. However, one critical bug in the splitter's multi-marker stripping logic will corrupt verse text when a verse contains multiple markers and the first marker is a cleanup-only (strip) operation. The marker positions become stale after text modification, causing subsequent strips to remove the wrong characters.

## Critical Issues

### CR-01: Stale marker positions after stripping in `fix_verses` corrupt verse text

**File:** `bibliavox/text/splitter.py:122-159`
**Issue:** When a verse contains multiple verse markers and the first marker is a "cleanup" operation (target verse exists → strip marker), the code modifies `current_text` at `marker.position` but subsequent markers still hold positions computed from the *original* text. After the first strip shortens the text, all subsequent marker positions are off by the length of the removed marker, causing the wrong text region to be stripped or split.

Example scenario with text `"Superscription 2) text 3) more"` where both verse 2 and 3 exist:
- Marker 1 (`2)`) at position 15, length 2 → strip removes chars 15-17 → text becomes `"Superscription text 3) more"` (shifted left by 2)
- Marker 2 (`3)`) still reports position 23 (from original text), but in the shortened text position 23 points to `"or"` — stripping chars 23-25 corrupts the verse

**Fix:**
```python
# In fix_verses(), track cumulative offset from stripped markers
for verse_record in sorted(verses, key=lambda v: v["verse"]):
    text = verse_record["text"]
    markers = detect_markers(text)

    if not markers:
        output_records.append(verse_record)
        stats["unchanged"] += 1
        continue

    # Track offset caused by prior strips in this verse
    offset = 0
    current_text = text
    split_occurred = False
    for marker in markers:
        adjusted_pos = marker.position + offset
        if marker.target_verse in existing_verses:
            # Target verse exists — strip marker, update offset
            current_text = (
                current_text[:adjusted_pos]
                + current_text[adjusted_pos + len(marker.raw_match):]
            )
            offset -= len(marker.raw_match)
            stats["cleaned"] += 1
        else:
            # Target verse missing — split
            before = current_text[:adjusted_pos].strip()
            after = current_text[adjusted_pos + len(marker.raw_match):].strip()
            output_records.append({
                "book": book, "chapter": chapter,
                "verse": verse_record["verse"], "text": before,
            })
            output_records.append({
                "book": book, "chapter": chapter,
                "verse": marker.target_verse, "text": after,
            })
            existing_verses.add(marker.target_verse)
            stats["split"] += 1
            split_occurred = True
            break

    if not split_occurred:
        verse_record["text"] = current_text.strip()
        output_records.append(verse_record)
```

## Warnings

### WR-01: `PATTERN_N` regex can produce false positive matches on mid-word digit sequences

**File:** `bibliavox/text/splitter.py:23`
**Issue:** `PATTERN_N = re.compile(r"\b(\d+)\)")` uses `\b` (word boundary) which matches between a non-word character and a digit. This means sequences like `"abc12)"` won't match (no boundary before `1`), but `"112)"` in a string like `"reference 112)..."` would match `"112)"` if preceded by a space. More critically, this pattern will match any `\d+)` anywhere in the text — including footnote references, parenthesized numbers, or Hungarian ordinal indicators — not just verse markers. For example, text like `"a 3) zsoltár"` where `3)` is a genuine verse marker would also match `"zsoltár"` false positives like `"1) kezdet"` if present. The current test data doesn't cover false-positive scenarios.

**Fix:** Consider adding context-aware constraints (e.g., require the match to be at the start of text or preceded by specific delimiters), or validate detected markers against expected verse numbers for the chapter:
```python
# Example: only match N) at start of text or after specific delimiters
PATTERN_N = re.compile(r"(?:^|(?<=[\s\.]))(\d+)\)")
```

## Info

### IN-01: `chapter_count` field in `versification.json` is redundant with `chapters` dict length

**File:** `data/reference/versification.json:1-75`
**Issue:** Each entry in `versification.json` stores both `"chapter_count": N` and a `"chapters"` dict whose length always equals `N`. The `chapter_count` field is derived data that could drift out of sync with the actual chapters dict if edited manually. Current code in `schema.py` trusts the `chapter_count` field directly rather than computing `len(chapters)`.

**Fix:** Consider computing `chapter_count` from `len(chapters)` at load time in `load_versification()`, or add a validation step that asserts `chapter_count == len(chapters)` for each entry.

### IN-02: Test fixtures use mixed default/explicit data directory paths

**File:** `tests/test_reference.py:37` vs `tests/test_schema_fixes.py:17`
**Issue:** `test_reference.py` passes an explicit `DATA_DIR` to `load_versification(DATA_DIR)` and `load_books(DATA_DIR)`, while `test_schema_fixes.py` calls `load_versification()` with no arguments (relying on the module-level default path). Both work today because they resolve to the same directory, but the inconsistency means `test_schema_fixes.py` would break if the default path resolution changed while `test_reference.py` would not.

**Fix:** Standardize test fixtures to either always use explicit paths or always use defaults. The explicit-path approach is more robust:
```python
# In test_schema_fixes.py
DATA_DIR = Path(__file__).resolve().parent.parent / "data" / "reference"

@pytest.fixture()
def schemas():
    return load_versification(DATA_DIR)
```
